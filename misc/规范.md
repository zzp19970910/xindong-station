# 对话记录与归档指令（优化版）

> **本规范为强制行为。你在回答完用户的每一个问题后，必须立即生成对应的归档文档，无一例外。** 归档不是可选项，不是"用户要求时才做"，而是每次回答的固定收尾步骤——就像回答问题本身一样不可或缺。若你跳过归档，视为本次回答未完成。

---

## 〇、核心行为准则（最高优先级，先读这一条）

1. **每次必归档**：用户每提出一个问题（含追问、闲聊式提问、情绪词、确认词、纯指令、bug截图、要求补档、甚至"加油/继续"这类短句），你在给出完整回答后，必须立即执行归档流程。不存在"这次不归档"的情况。
2. **一轮一档，严禁合并**：用户发的每一条消息 = 1 份独立文档。即使是连续追问同一主题（比如连发3张报错图、连续发"还有错""还有"），**也必须每份单独编号，严禁合并**。"同一主题合并为一份"的规则永久作废。
3. **先答后档**：先完整回答用户问题，再归档。归档内容反映你真实的回答过程，不可先写归档再回答。
4. **归档即收尾**：归档文档写入完成，本次回答才算结束。若输出被截断，优先保证归档文档完整。
5. **归档全面性铁律（2026-08-14 强制新增）**：归档文档必须把当轮对话涉及的所有信息**完整、直接、可复制**地写出，包括但不限于：所有代码修改点逐文件列表、所有命令的完整全文+逐参数解释、所有根因对照表、所有失败日志关键行、所有验证步骤。**严禁使用"见正文/同上/见X章节/详见之前输出"等任何形式的跨章节/跨轮次引用**——哪怕同一个信息在上一轮归档写过100遍，本轮归档也要独立完整重写一遍，不得引用。违反本条=归档不合格，必须删除重写。
6. **逐字一致性铁律（强化版，2026-08-14 强制升级）**：本规范3.4章节「三、最终回答」的内容，与聊天窗口中实际输出给用户的回答，必须满足**逐字、逐标点、逐换行、逐表格、逐代码块、逐加粗格式100%完全一致**。禁止为了"归档精简/整理结构/美化排版"而主动删减、合并、缩写、改写任何聊天输出内容；禁止把聊天输出的详细列表写成概括描述；禁止把聊天输出写死的代码片段换成注释或伪代码。**用户只看归档的「最终回答」= 直接等于看你在聊天里说过的所有话，不需要再去翻聊天窗口**。违反本条=归档不合格，必须删除重写。
7. **思考过程完整性铁律（2026-08-14 强制新增）**：本规范3.3章节「二、思考过程」必须完整覆盖**5个强制维度**（问题拆解、信息收集、方案对比、决策推理、潜在风险），每个维度至少3行内容，严禁只写最终结论不写推理链路，严禁写"无/不适用"凑数（真不适用的必须写清楚为什么不适用的具体理由，至少1行）。思考过程必须如实记录被否决的中间方案、踩过的坑、一开始的错误假设，绝不允许只写光鲜的最终结论。**缺任何1个维度或维度内容为空=归档不合格，必须删除重写**。
8. **输出倒逼归档强制机制（2026-08-14 强制执行）**：每轮回答写完、归档文档真的写入磁盘完成后，**必须在聊天输出的最后一行（紧跟在回答内容之后）加一句固定格式的归档确认句**，格式严格为：`✅ 归档已完成：对话记录/YYYY-MM-DD/XXX-问题简述.md | 规范合规：√全面 √逐字一致 √思考5维度`（其中日期/编号/文件名必须和真的归档文件完全对应）。**没写完归档绝不允许输出这句话；只要输出了这句话，就证明归档真的落地了**。用户每轮都能看到这句话，相当于透明监督，无需再专门发"记录记录"催促。违反本条=本轮回答未完成，必须立刻补归档并补发确认句。
9. **多行命令生成脚本铁律（2026-08-14 强制新增）**：当需要用户执行的命令满足以下任一条件时，**必须生成独立可直接运行的脚本文件写入磁盘**，绝不允许只在聊天窗口列一堆命令让用户手动一条条复制执行：① 连续≥3条命令（含管道/重定向/分号拼接的多行算多条）；② 含条件判断/循环/变量定义等脚本逻辑（不是纯单条命令）；③ 命令总长度超过一屏（≈800字符）；④ 用户明确说"给个一键脚本/批量执行/自动跑"。脚本必须用户**双击或一条命令就能跑完所有步骤**，中间不需要任何手动复制粘贴或交互输入。违反本条=解决方案不合格，必须补写脚本。
10. **单行命令交付铁律（2026-08-14 用户强制要求，最高优先级）**：**绝对不允许把.ps1/.bat/.py脚本的多行内容直接贴在聊天里让用户复制粘贴到命令行窗口执行**（多行注释/括号配对/中文编码/换行拆分会导致100%报错）。正确交付流程必须严格是三步，缺一不可：① 先用Write工具/命令把脚本完整写入磁盘scripts/目录；② Windows .ps1脚本必须用**UTF-8 with BOM**编码写入（防止中文乱码）；③ 聊天里**只给用户一条纯文本单行命令**，形式固定为：`Set-ExecutionPolicy Bypass -Scope Process -Force ; powershell -NoProfile -NonInteractive -ExecutionPolicy Bypass -File "脚本绝对路径"`——用户复制这一整行粘贴回车即可，全程不需要打开脚本文件、不需要复制多行内容、不需要改任何字符。违反本条=解决方案严重不合格，必须立刻重写脚本+重新给单行命令，且属于第六章第10条同级严重违规，下轮必须道歉。
11. **执行命令优先交付铁律（2026-08-14 用户强制要求，最高优先级，优先级高于所有其他铁律）**：当用户明确需要执行操作（包括但不限于"接下来执行哪个/给我命令/跑一下/报错了怎么办/现在做什么/启动后做什么"这类直接或间接要求），**必须把「用户可直接复制的单行执行命令」放在聊天输出的第一段最开头最显眼位置（第一句话）**，绝对不允许出现以下任何一种顺序：① 先贴长篇思考过程/分析/根因表/代码修改，再给命令；② 先写归档/先修改规范/先做其他磁盘写入操作，再给命令；③ 先让用户做额外准备工作（填Token/改文件/开端口），再给命令；④ 命令藏在文章中间/结尾，用户翻半天才能找到。命令必须第一时间给，给完命令后才能开始做后续的读代码/改代码/写归档/更新规范等所有其他操作。**用户打开聊天窗口第一眼看到的，必须就是能直接复制的命令文本，不是别的任何东西**。违反本条=本轮回答直接不合格，必须立刻删除已输出内容，重新按"命令第一段先给"的顺序组织输出，且属于第六章第11条严重违规，下轮必须公开道歉。
12. **问题记忆库同步铁律（2026-08-14 用户强制要求，每次犯错必写，防止重复踩坑）**：**每次遇到任何新的错误/踩坑/FAIL（包括但不限于：测试用例FAIL、代码编译错误、脚本执行报错、用户批评规范违规、HTTP接口异常、Spring事务/数据问题、IDEA工具问题、路径冲突/映射问题、数据污染、PowerShell编码问题等），在回答完用户问题+完成本轮归档后，必须立刻同步更新「历史问题记忆库避坑指南」文档**（默认路径：`f:\docker\xindong-station\docs\历史问题记忆库避坑指南VX.Y.md`，若路径调整需同步更新本规范）。更新要求（缺一不可）：① 先判断错误属于9大类（A事务/B编译/C脚本/D测试参数/E路径/F请求体/G数据/H IDEA工具/I规范）中的哪一类；② 在对应大类下追加新条目（编号顺序递增，如A006/B005/C008等），条目必须至少包含5小节：现象（可直接复制的错误日志原文）、根因（3行以上深层原因）、最终解法（可直接落地的最小修改方案）、30秒快速定位（下次再遇到时一条Grep/命令立刻确认的方法）、下次禁止犯的错（明确禁止动作）；③ 更新记忆库顶部"大类索引"表格对应大类的"问题数"+1。**绝对不允许"这次遇到了，下次再记""忙忘了""问题小不值得记"**——哪怕只是"多写了一个分号导致脚本报错"这种低级错误，也必须完整写入记忆库。违反本条=本轮归档合格但流程不合格，下轮必须道歉+补记记忆库，且重复违反2次以上视为规范违规第12条严重违规。

## 一、目录结构与创建规则

### 1.1 工作目录
在**当前工作目录**下创建专属归档目录，无需用户指定路径：

```
工作目录/
└── 对话记录/
    └── 2026-08-07/              ← 按当天日期（YYYY-MM-DD）
        ├── 001-问题简述.md
        ├── 002-问题简述.md
        └── ...
```

### 1.2 创建流程
每次归档前执行以下检查：

1. 读取当前系统时间，确定日期（YYYY-MM-DD）。
2. 检查 `对话记录/<日期>/` 目录是否存在——不存在则先创建。
3. 扫描该目录下已有文件，确定下一个可用编号（从 001 起，三位数递增）。
4. 若目标编号已被占用，编号 +1 直到不冲突。
5. 写入文件。

> 日期以**当前实际系统时间**为准，不使用用户消息中的示例日期。

## 三、文档内容结构（六部分，缺一不可）

### 3.1 文档头（YAML front matter）

文件最顶部，紧跟三横线：

```yaml
---
title: 完整问题描述（不截断、不缩写）
date: 2026-08-07 14:30:00
number: "001"
tags: [标签1, 标签2]
status: completed
---
```

- `date`：归档时的实际时间，精确到秒。
- `tags`：2-5 个关键词标签，便于检索。
- `status`：固定为 `completed`。

### 3.2 一、原始问题

**逐字完整记录当轮用户提出的原始问题**，保留原始表达，不做润色或改写。严格一份归档 = 当轮一条用户消息，禁止把其他轮的问题写到本份文档里。归档编号和对应轮次 1:1 对应。

### 3.3 二、思考过程

**🔴本章节为强制合规项（对应〇、核心行为准则第7条），缺任何1个维度=归档不合格，必须删除重写。**

这是文档的**核心部分**，须尽可能详尽。如实记录推理链路，包括被否定的中间思路——不要只写最终结论。**必须100%覆盖以下5个强制维度（每个维度至少3行内容），第6个关键判断维度如无则写清楚不适用的理由（至少1行）**：

- **问题拆解**：把问题分解成了哪些子问题？分解依据是什么？先判断是共同根因还是独立根因？怎么分的优先级？（≥3行）
- **信息收集**：是否查阅了资料？查了什么文件/日志/代码？精确到行号/路径？收集动作的实际输出是什么？关键发现是什么？（≥3行）
- **方案对比**：是否存在多种解法？至少列出2种以上方案的对比表格，写清各自的优缺点、适用场景、风险等级。只有1种方案的必须写清楚为什么没有其他方案的具体理由（≥3行+对比表格，无表格视为不合格）。
- **决策推理**：为什么选了最终方案？排除了哪些方案？排除的具体理由是什么？决策的关键依据是哪条日志/哪行代码/哪个文档？（≥3行）
- **潜在风险**：预判了哪些风险或边界情况？每个风险的触发条件是什么？如何应对/兜底？改完代码后影响范围是什么？会不会破坏其他模块？（≥3行）
- **关键判断（可选但推荐）**：过程中做了哪些重要判断？判断依据是什么？

### 3.4 三、最终回答

**🔴本章节为强制合规项（对应〇、核心行为准则第5、6条），出现任何跨章节引用/逐字不一致=归档不合格，必须删除重写。**

完整记录最终给出的解决方案或答复：

- 按逻辑层次组织，善用标题、列表、表格。
- 涉及代码用对应语言代码块包裹并标注语言类型。
- 涉及步骤须编号清晰、可操作。
- 关键结论用**加粗**标注。
- **归档全面性硬约束**：解决方案、所有代码修改点逐文件列表、所有命令的完整全文+逐参数解释、所有根因对照表、所有失败日志关键行、所有验证步骤等所有信息，必须**完整、直接、可复制**写在本节中，**严禁使用"见正文"、"见X章节"、"同上"、"详见之前输出"等任何形式的跨章节/跨轮次引用**——哪怕同一个信息在上一轮归档写过100遍，本轮归档也要独立完整重写一遍，不得引用。
- **归档最终回答=聊天输出100%逐字一致性铁律（强化版，2026-08-14 用户强制升级）**：本节「最终回答」内容必须和聊天窗口中实际输出给用户的回答**逐字、逐标点、逐换行、逐表格、逐代码块、逐加粗格式100%完全一致**。禁止为了"归档精简/整理结构/美化排版"而主动删减、合并、缩写、改写任何聊天输出内容；禁止把聊天输出的详细列表写成概括描述；禁止把聊天输出写死的代码片段换成注释或伪代码。**用户只看归档的「最终回答」= 直接等于看你在聊天里说过的所有话，不需要再去翻聊天窗口**。违反本条视为归档不合格。
- **反向生成法推荐流程（100%保证逐字一致）**：先写聊天输出草稿 → 完整复制到本节 → 再从本节原封不动复制回聊天窗口输出。从源头保证两边100%一致，绝无偏差。

#### 3.5.1 多行命令生成脚本强制规范（对应〇、核心行为准则第9条，命中任一条件必须生成）

- ③ 命令全文总长度≈超过一屏（超过800字符或超过20行）；
- ④ 用户明确要求"给个一键脚本/批量执行/自动跑/写个ps1/py/sh"。

**脚本命名规范**：
| 操作系统 | 扩展名 | 命名格式 | 示例 |
|---------|--------|---------|------|
| Windows（主用） | `.ps1`（PowerShell） / `.py`（跨平台逻辑复杂时） | `NNN-功能简述-环境.ps1`，NNN用本轮归档3位编号，保持可追溯 | `053-重置M03脏数据并跑全量测试.ps1` |

**脚本存放路径**：

- 如果用户明确指定了脚本放其他位置（比如任务X/代码/下），按用户指定路径放，同时在归档的「最终回答」里明确写清完整路径。

**脚本内容强制要求（8项，缺1=脚本不合格）**：
1. **编码+头部（Windows .ps1必须）**：文件保存为 **UTF-8 with BOM** 编码（防止中文路径/中文输出乱码）；第一行必须加 `#Requires -Version 5.1` 或更高，第二行加 `$ErrorActionPreference = "Stop"`（遇到任何错误立刻停止，绝不往下跑污染环境）；
2. **逐步骤注释**：每个关键步骤前一行写 `# === N. 步骤描述 ===`，比如 `# === 1. 停止正在运行的Java后端进程 ===`，用户打开脚本一眼就知道每一步在干嘛；
3. **cd到工作目录兜底**：脚本开头前3步内必须有 `Set-Location "f:\docker"`（或实际工作目录的绝对路径），防止用户在其他目录右键运行脚本导致相对路径找不到文件；
4. **错误处理+返回码**：每个关键命令执行后必须检查退出码（PowerShell用 `if ($LASTEXITCODE -ne 0)`，Python用 `subprocess.check_call()`/检查returncode），失败时**红色打印错误信息 + 非0退出码 + 明确告诉用户哪一步失败了**，绝对不能静默失败继续往下跑；
5. **成功提示**：全部步骤跑完无错误时，最后**绿色打印成功提示**（比如 `Write-Host "✅ 所有步骤执行完成！共N步，全部通过。" -ForegroundColor Green`），让用户不用翻输出日志就知道成没成；
6. **禁止交互输入**：脚本运行全程不能有任何 `Read-Host` / `input()` 等待用户手动输入的地方——所有参数要么在脚本顶部用`$XXX = "硬编码值"`写死（带注释说明可以改哪里），要么通过命令行参数传入（带默认值），保证用户**双击/一条命令直接跑到底**；
7. **幂等可重复执行**：脚本必须支持重复跑不炸——比如"停止服务"步骤如果服务已经停了不能报错、"创建目录"已存在不能报错、"删文件"不存在不能报错，所有操作前先判断状态再执行；
8. **一键执行说明**：脚本头部注释区必须写清楚**2种执行方式（双击/命令行）**，比如：
```powershell
<#
.SYNOPSIS 本脚本功能：XXX
.EXAMPLE 执行方式1（推荐）：右键本文件 → "使用PowerShell运行"
.EXAMPLE 执行方式2：打开PowerShell → 输入 & "f:\docker\scripts\053-XXX.ps1" 回车
#>
```

**脚本生成后的配套动作（缺一不可）**：
- ① 真的把脚本写入磁盘（路径+命名严格按上述规范），不能只在聊天里贴代码块说"你自己保存成ps1"；
- ② 在「最终回答」里**明确给出脚本完整绝对路径 + 2种执行方式**；
- ③ 在归档的「四、命令行执行」章节中，对脚本本身也按"命令N"格式记录：完整路径/逐段解释/（如果我自己先跑过的话）执行结果/结果说明；
- ④ 如果命令行数<3条但用户要脚本，也按本规范生成，不限制下限。

# 如何在 macOS 上用 Homebrew 安装 Python 3.12 并配置虚拟环境

## 一、原始问题

第 1 轮：在 macOS 上怎么用 Homebrew 装 Python 3.12，然后建一个虚拟环境？

## 二、思考过程

**问题拆解**：拆为三步——安装 Homebrew（可能已装）、安装 Python 3.12、创建并激活虚拟环境。

**方案对比**：
- 方案 A（Homebrew）：macOS 主流，版本管理方便，社区支持好。
- 方案 B（pyenv）：可装多版本，但配置复杂，对新手不友好。
- 方案 C（官方安装包）：简单但难管理多版本。

**决策推理**：用户明确说 Homebrew，且 macOS 场景下 Homebrew 是首选，选方案 A。pyenv 作为进阶建议补充提及。

**潜在风险**：Homebrew 未安装时直接 brew install 会报错，需先检查；PATH 可能未正确指向新版本，需验证。

## 三、最终回答

分三步操作：

1. 检查 Homebrew 是否已安装：
```bash
brew --version
```
若提示找不到命令，先安装 Homebrew（见命令 1）。

2. 安装 Python 3.12：
```bash
brew install python@3.12
```

3. 创建并激活虚拟环境：
```bash
python3.12 -m venv myenv
source myenv/bin/activate
```

**关键点**：激活后命令行前缀会出现 `(myenv)`，表示虚拟环境已启用。

## 四、命令行执行

#### 命令 1：安装 Homebrew
**完整命令**：
\```bash
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
\```
**逐参数解释**：
| 参数/片段 | 含义 |
|-----------|------|
| `/bin/bash -c` | 用 bash 执行后面的字符串 |
| `curl -fsSL` | 静默下载脚本，-f 失败不输出错误页 |
**执行结果**：安装成功，提示 next steps。
**结果说明**：符合预期，按提示将 Homebrew 加入 PATH 即可。

## 五、补充说明

- Homebrew 官方文档：https://docs.brew.sh
- 后续待办：用户如需多版本切换，可再装 pyenv。

- **用户提了新的文档要求，必须更新本规范**：如果用户说「以后要存到另一个目录」「命名风格改一下」「内容要完整/要精简」，立即更新本规范.md的对应章节，不是只临时执行一次。每次新要求进规范后，需在聊天末尾明确告知用户「XX要求已写入规范第X章第X节」。

### 7.4 归档与聊天输出的逐字一致性铁律（2026-08-14 用户强制要求，与7.3并列双铁律）

> **核心目标**：用户只看「对话记录/日期/XXX.md」归档，就能获得和看聊天窗口完全一样的所有信息。绝对不允许出现「用户看了归档还要翻聊天窗口对照、发现说的和记的不一样」的情况。

本节和 7.3「正式文档完整无删减原则」两条同时强制执行，适用范围不同：
- 7.3 管：**项目正式文档 vs 聊天输出** → 给产品/开发看的交付物，不能精简
- 7.4 管：**对话归档文档 vs 聊天输出** → 给QA自己/追溯过程看的归档，必须逐字一模一样

| 维度 | 铁律要求 | 反例（违规，发现即归档不合格） |
|------|---------|------------------------------|
| 内容量 | 100% 对齐，一个字不能少 | 聊天输出写了「5处代码修改+每处具体文件:行号」→ 归档概括成「修复5处代码」（删掉具体路径=违规） |
| 表格 | 列数、行数、单元格内容逐字一致 | 聊天输出列了 CONFIG 8 个具体值的注释（POOR_A必须是909 coins=100）→ 归档注释删掉只写占位（违规） |
| 代码块 | 代码字符逐字一致，不能替换 | 聊天输出给了真实的 PowerShell 命令（`cd f:\... ; ./scripts/06-F-Stop...`）→ 归档用「停止服务命令」几个字代替（违规） |
| 结构 | 标题、列表层级、加粗/分隔线 100% 保留 | 聊天输出用了分隔线 `---` + 三类 emoji 分块（✅/⚠️/🤔）→ 归档去掉 emoji 合并成一段（违规） |
| 结论 | 所有加粗强调语句逐字保留 | 聊天输出反复强调「909 coins必须=100不能是1000」「C1不能和A同情侣」→ 归档没写（违规） |

> **最终判定原则**：把聊天窗口输出内容 Ctrl+A 全选复制，粘贴到归档的「三、最终回答」下面，diff 结果=0 条差异=合格。任何>0的差异=不合格，必须重写。

## 八、防遗漏强化（再次强调）

- **没有例外**：无论问题多简单（哪怕一句话能答、哪怕只是情绪词/确认词如"加油""继续""好的"），都要归档。简单问题的"思考过程"可简短，但结构不可缺。
- **不要等用户提醒**：归档+正式文档双写是你的主动行为，不是被要求才做的。
- **严禁合并任何轮次**：用户每一条消息必须一份独立文档，哪怕连续 10 条都是同一个报错的截图/补充，也必须每条单独编号递增。"同一主题合并""连续追问合并"全部作废，发现合并视为违反规范。
- **不要用"将在对话结束后统一归档"等拖延话术**：回答完立即双写（正式文档+归档），当场完成。
- **正式文档优先**：如果只能二选一（比如输出被严重截断），优先保证正式文档完整，其次保证对话归档完整。
