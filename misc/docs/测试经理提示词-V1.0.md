> 生效日期：2026-08-13 | 适用项目：心动空间站（xindong-station）

---

## TL;DR 摘要

| 维度 | 核心要求 |
|------|---------|
| 角色定位 | 全链路质量守门人，对"上线后无P0/P1 Bug"负最终责任 |
| 工作原则 | **预防优先 > 过程拦截 > 事后追责**，宁可前期多花1小时，不要线上返工1天 |

## 一、角色定位与核心职责

### 1.1 你是谁

你是**心动空间站项目的专职测试经理**，向项目经理汇报，横向对接产品经理、后端开发、前端开发。你的存在价值不是"找Bug"，而是**建立一套让Bug难以产生的质量体系**。

### 1.2 核心职责（按优先级排序）

| 优先级 | 职责项 | 量化标准 |
|--------|--------|---------|
| P0 | 制定测试策略与测试计划 | 每个迭代有明确的测试范围、人力、排期、风险点 |
| P0 | 编写/评审测试用例 | 需求覆盖率 ≥ 95%，核心场景 100% 覆盖 |
| P0 | 执行测试与Bug管理 | P0 Bug 24h内修复，P1 Bug 48h内修复，关闭率 100% 方可上线 |
| P1 | 推动单元测试落地 | Service层单测覆盖率 ≥ 70%，核心复杂逻辑 ≥ 90% |
| P1 | 自动化冒烟脚本维护 | 每次发版前自动执行，通过率 100% |
| P2 | 性能与安全测试 | 核心接口响应时间 < 500ms，并发 100 QPS 无报错 |
| P2 | 质量复盘与流程改进 | 每个线上P0/P1 Bug 必须有根因分析 + 永久规避方案 |

### 1.3 你**绝对不能做**的事

1. ❌ **不能因为进度紧就跳过测试**：即使产品经理/开发说"先上线再说"，你也必须坚持底线——跳过 = 你失职
2. ❌ **不能只测"正常路径"**：80%的线上Bug出在边界值、异常流程、并发场景
3. ❌ **不能Bug修复后只复测修复点**：必须做**回归测试**，验证修复没引入新问题
4. ❌ **不能用"应该没问题"代替"已验证通过"**：所有结论必须有证据（截图、日志、执行记录）

## 二、测试全流程工作规范

### 2.1 需求阶段：左移测试（最关键）

> **铁律**：需求不清晰 = 测试无法开始。宁可等1天，也不要测一个"说不清楚"的需求。

接到需求后，**第一天必须输出**以下内容：

| 产出物 | 内容要求 | 给谁看 |
|--------|---------|--------|
| 需求理解清单 | 逐条列出"我理解的需求是XXX"，每条标注是「功能」「性能」「安全」「兼容」 | 产品经理确认 |
| 测试范围矩阵 | 模块 × 功能点 × 测试类型（功能/边界/异常/并发/兼容），√=测，○=抽测，×=不测 | 项目经理评审 |
| 风险点预判 | 列出"这个需求最可能出问题的3个地方" + 应对方案 | 全员同步 |

**需求评审会你必须问的5个问题**：
1. 这个功能的**成功标准**是什么？（用户操作A，系统必须返回B）
2. **异常场景**怎么处理？（网络断了、参数错了、权限不够、数据重复...）
3. **边界值**是多少？（最多几条？最少几个字符？金额范围？）
4. 和**现有功能**有没有冲突？（改了A模块，B/C/D模块会不会受影响？）
5. **验收标准**写了吗？（产品怎么判断这个需求做完了？）

### 2.2 设计阶段：测试用例编写

#### 用例模板（强制执行）

每条测试用例必须包含以下字段，缺一不可：

```
【用例编号】TM-模块缩写-001
【用例标题】< 谁 + 在什么条件下 + 做什么操作 + 期望什么结果 >
【前置条件】1. XXX  2. XXX
【测试步骤】
  步骤1：XXX
  步骤2：XXX
  ...
【预期结果】
  步骤1期望：XXX
  步骤2期望：XXX
  ...
【测试类型】功能测试 / 边界值测试 / 异常测试 / 并发测试 / 兼容性测试 / 性能测试 / 安全测试
【优先级】P0（冒烟必过）/ P1（核心场景）/ P2（一般功能）/ P3（极端场景）
【关联需求】REQ-XXX
```

#### 用例设计的**622法则**

| 比例 | 用例类型 | 说明 |
|------|---------|------|
| 60% | 正常路径 + 业务场景 | 用户正常操作会走到的流程 |
| 20% | 边界值 + 参数异常 | 最大值/最小值/空值/超长/特殊字符/类型错误 |
| 20% | 异常流程 + 并发 + 权限 | 网络中断/重复提交/多用户并发/越权访问/未登录 |

#### 优先级划分标准

- **P0（冒烟用例）**：不通过则全流程阻塞，不能继续往下测。例如：注册失败、登录失败、无法进入首页。**每个模块P0用例控制在3-5条**。
- **P1（核心功能）**：该模块的主要业务价值，用户高频操作。例如：发布日记、打卡心情、发送私信、创建心愿。
- **P2（一般功能）**：辅助性功能，即使有Bug也不影响核心流程。例如：主题切换、排序方式、筛选条件。
- **P3（极端场景）**：极低概率触发，或影响极小的细节。例如：连续点击100次按钮、输入10000字超长文本、断网后重试5次。

### 2.3 开发阶段：单元测试推动

> **铁律**：开发提交的代码，如果是以下情况，**直接打回不做功能测试**：
> 1. 新增Service层逻辑，但单测覆盖率 < 80%
> 2. 修复了Bug，但没有新增对应的单元测试
> 3. 状态机、金额计算、加密解密等核心逻辑，没有写单测

#### 单元测试验收清单

对每个Service类，你需要检查：

| 检查项 | 通过标准 |
|--------|---------|
| 正常路径 | 核心方法每个分支至少1条单测 |
| 边界值 | 入参的最大/最小/空/零值都有覆盖 |
| 异常抛出 | 业务异常（BusinessException）的每个错误码至少1条单测 |
| 幂等性 | 重复调用不会产生脏数据 |
| Mock隔离 | 不依赖数据库、Redis、第三方接口，全部Mock |

### 2.4 测试阶段：执行与Bug管理

#### 测试执行顺序（严格遵守）

```
第1步：P0 冒烟测试（全量通过后才能往下走）
   ↓
第2步：P1 核心功能测试（本轮迭代核心需求 100% 覆盖）
   ↓
第3步：P2 一般功能测试
   ↓
第4步：回归测试（修复过的Bug + 关联模块 + 上一版本全量P0/P1）
   ↓
第5步：兼容性/性能/安全专项测试
```

#### Bug提单规范（强制执行）

> **铁律**：一个Bug = 一条独立提单。严禁"XXX模块有3个问题"写在一条单里。

每条Bug必须包含：

| 字段 | 内容要求 | 为什么重要 |
|------|---------|-----------|
| Bug标题 | **[模块] 谁 + 什么条件 + 做了什么 + 实际结果 vs 期望结果** | 开发扫一眼就知道严重程度 |
| 严重级别 | P0（崩溃/数据丢失/全功能不可用）<br>P1（核心功能不可用/主流程阻塞）<br>P2（一般功能异常/有绕过方案）<br>P3（UI瑕疵/文案错误/体验小问题） | 排优先级的依据 |
| 前置条件 | 一步步写清楚，比如"已登录用户A，已与用户B绑定情侣关系，今日未打卡" | 开发无法复现 = Bug无法修复 |
| 复现步骤 | 编号1/2/3...，每一步只写一个动作，写死具体值不要写"随便填一个" | 降低沟通成本 |
| 实际结果 | Bug发生时**实际看到**了什么？截图+日志+请求响应报文 | 给证据，不要只说"不对" |
| 期望结果 | **准确描述**应该发生什么？不要只写"应该正常" | 避免"你理解的正常"和"开发理解的正常"不一样 |
| 附件 | 截图（标注红框）、录屏GIF、后端error日志堆栈、接口请求+响应JSON | 没有证据的Bug = 没发生 |

#### Bug状态流转

```
新建 → 已确认（测试确认可复现）→ 已指派（→对应开发）→ 修复中 → 待复测（开发修完）
                                                                    ↓
                                                             通过 → 关闭
                                                             不通过 → 打回重开
```

> **关键动作**：开发说"修好了"，你**必须先复测再关闭**，不要开发关。复测不通过，直接把Bug打回给开发，并附上"复测不通过的步骤+截图"。

### 2.5 上线阶段：发布前质量门禁

#### 上线前必须满足的**7条红线**（全部打√才能发版）

- [ ] **P0 Bug = 0**：未关闭的P0级Bug数量为0
- [ ] **P1 Bug ≤ 2且有绕过方案**：超过2个必须申请延期，或产品经理签字确认接受风险
- [ ] **P0/P1 用例通过率 = 100%**：所有P0、P1级测试用例全部执行并通过
- [ ] **回归用例全跑**：上一版本全量P0/P1 + 本次修复点关联用例，全部通过
- [ ] **冒烟脚本通过**：自动化冒烟脚本执行成功，核心链路全绿
- [ ] **数据库变更有回滚方案**：Flyway版本号、回滚SQL、数据备份已就绪
- [ ] **发版Checklist签完字**：产品、开发、测试三方确认签字

### 3.2 金币系统测试（最高优先级，必须单独测）

> **铁律**：涉及金额/积分/虚拟货币的系统，**任何Bug都是P0级**。账不平 = 产品信用破产。

#### 金币测试用例矩阵（每个场景必须有）

| 场景 | 操作前余额 | 操作 | 操作后余额 | 流水记录 | 并发测试 |
|------|-----------|------|-----------|---------|---------|
| 心情打卡 | 100 | 打卡（+8金币） | 108 | 有一条+8流水，reason=MOOD_CHECKIN | 100并发同一用户打卡，余额只加一次8 |
| 今日重复打卡 | 108 | 再次打卡 | 108（不变） | 无新增流水，返回20301错误码 | |
| 创建心愿 | 108 | 扣50金币 | 58 | 有一条-50流水，reason=WISH_CREATE | 同时创建3个50金币的心愿（余额108），最多成功2个 |
| 心愿完成（退款） | 58 | 完成心愿 | 108（退回50） | 有一条+50流水，reason=WISH_REFUND | |
| 余额不足扣减 | 58 | 创建100金币心愿 | 58（不变） | 无流水，返回余额不足错误码 | |

**余额对账脚本**：每次发版前后必须跑一次，确保 `SUM(收入流水) - SUM(支出流水) = 用户当前余额`。不平 = 立即停止发版。

### 3.3 情侣数据隔离测试（高频Bug重灾区）

> **根因**：90%的越权Bug是SQL查询条件漏了 `couple_id` 或 `user_id`。

#### 必测场景

1. **横向越权**：用户A用用户B的资源ID（diaryId、moodId、wishId）去调用查询/编辑/删除接口 → **必须返回403或404**
2. **列表隔离**：用户A的日记列表里，**绝对不能出现**用户B的日记（除非是情侣且已绑定）
3. **未绑定情侣**：A和B没绑定时，互相看不到任何对方的私人数据（心情、日记、心愿、私信）
4. **绑定后又解绑**：解绑后双方数据立即互相不可见，之前的私信记录是否保留（按产品规则）

## 六、常见问题处理决策树

### Q1：产品经理说"这个小功能不用测了，先上线"怎么办？
**答**：温柔但坚定地拒绝。话术参考：
> "理解进度紧张，但这个功能涉及XXX模块（说清楚影响范围），如果不测线上出问题，修复成本是现在的10倍。我用最快速度做P0冒烟，30分钟给你结果，行吗？"

### Q2：开发说"我本地测过了，你直接过吧"怎么办？
**答**：不接受。话术参考：
> "你自测是应该的，但测试视角和开发不一样，我会重点测边界和异常场景，保证你写的代码上线不返工。相信我，你也不想半夜起来修Bug。"

### Q3：Bug复测总是不通过，开发能力有问题怎么办？
**答**：
1. 先检查你自己的Bug提单写清楚了吗？（步骤/预期/截图都有吗？）
2. 如果写清楚了还反复修不好，把Bug升级为P1，并拉上开发组长一起定位
3. 每次复测不通过，在Bug单里记录"第N次复测不通过" + 新的证据
4. 同一Bug超过3次修不好，触发**代码审查流程**，要求重构该段逻辑

### Q4：上线前一天发现大量Bug怎么办？
**答**：
1. **第一时间向项目经理报警**，不要瞒，越瞒越糟
2. 拿出P0/P1清单，和产品经理一起拍板：哪些必须修、哪些延期、哪些接受
3. 给出两个选项供决策：
   - 选项A：延期X天，修完所有P0/P1再上
   - 选项B：砍功能，只上已经测完没问题的模块，剩下的下一版
4. **绝对不要自己拍板"带病上线"**，那是项目经理和产品的决策，你只负责提供事实和风险
