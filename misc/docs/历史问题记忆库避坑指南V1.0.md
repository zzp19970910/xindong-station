## A. 🏛 Spring事务传播/回滚类（最高频，本次9条FAIL根因）

### A001 · 外层@Transactional + try-catch吞addCoins异常 + REQUIRED = Transaction silently rolled back
**现象**：所有写操作（登录/打卡/日记/纪念日/情书/问答）接口返回50002，DEBUG后缀显示：
```
Transaction silently rolled back because it has been marked as rollback-only
```
**根因**：经典Spring事务坑：
```java
@Transactional // 外层主事务
public X doMain() {
    saveBusinessData();
    try {
        coinService.addCoins(...); // 默认Propagation.REQUIRED加入外层事务
    } catch (Exception e) {
        log.warn("送币失败不影响主业务"); // ← addCoins抛BusinessException已标记外层事务rollback-only
    }
    return ok; // ← Spring commit→发现被标记rollback-only→直接崩
}
```
**最终解法**：CoinService.addCoins加`propagation = Propagation.REQUIRES_NEW` → 金币在独立新事务跑，回滚只影响金币独立事务，外层主业务事务100%正常提交。
```java
@Transactional(propagation = Propagation.REQUIRES_NEW, 
               isolation = Isolation.REPEATABLE_READ, rollbackFor = Exception.class)
public int addCoins(Long coupleId, CoinReason reason, ...)
```
**30秒快速定位**：日志Grep `Transaction silently rolled back` → 直接确认 → 检查CoinService.addCoins上有没有REQUIRES_NEW注解 + 是不是public方法 + 有没有Rebuild。
**出现时间**：2026-08-14 16:48→17:48，跨071-079共9轮才修完。
**下次禁止犯的错**：不要在外层@Transactional主方法里 try-catch 吞REQUIRED内层方法的RuntimeException。要么改内层REQUIRES_NEW，要么不要吞异常。

### A002 · 手动调 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly() 然后抛异常+外层吞 = 100%崩rollback-only
**现象**：和A001一样，但不是Spring自动标记的，是代码里手动写的：
```java
catch (Exception e) {
    TransactionAspectSupport.currentTransactionStatus().setRollbackOnly(); // ← 手动调
    throw new BusinessException(ErrorCode.XXX); // ← 然后抛
}
```
然后上层catch住想继续→commit还是崩。
**根因**：手动setRollbackOnly后，不管你抛不抛异常、有没有被catch，当前事务的rollbackOnly位=1，commit时100%回滚+抛UnexpectedRollbackException/Transaction silently rolled back。
**最终解法**：**项目中禁止任何地方出现setRollbackOnly关键词**。要回滚就直接抛BusinessException（RuntimeException），Spring事务默认自动回滚。不需要手动。
**30秒快速定位**：全项目Grep `setRollbackOnly` → **必须0命中**，不为0就删光所有。
**出现位置**：本次CoinService.java 2处 + WishService.java 2处=共4处手动调，全删后才稳定。
**下次禁止犯的错**：任何代码评审时，出现setRollbackOnly关键词直接打回重写。

### A003 · 悲观锁@Lock + REQUIRES_NEW 顺序优先级问题
**现象**：担心REQUIRES_NEW开新事务后，@Lock(LockModeType.PESSIMISTIC_WRITE)会不会在新事务外执行？
**根因**：Spring切面执行顺序：@Transactional（切面）先开新事务/连接，然后在事务内执行Repository方法时，@Lock（Hibernate/JPA级别）才生效→SELECT ... FOR UPDATE在新事务里锁行，没问题。
**最终解法**：顺序正确，不需要额外配置。只要@Transactional(REQUIRES_NEW)加在Service public方法上+方法内调用Repository的@Lock方法，顺序天然正确。
**30秒快速验证**：MySQL `show engine innodb status` 看TRANSACTIONS段里的锁等待事务ID，如果有两个不同TRX ID（外层主业务1个，addCoins独立1个）→REQUIRES_NEW生效。
**下次禁止犯的错**：不要把@Transactional加在非public方法上（lombok @Data生成的是public没问题，自己写package-private的@Transactional不生效）。

### A004 · noRollbackFor 过度使用风险
**现象**：如果外层主方法加`@Transactional(noRollbackFor = BusinessException.class)`想解决A001→虽然能解决rollback-only，但主业务本身抛BusinessException时（比如打卡重复应该回滚+返回20301）→反而不回滚→脏数据！
**根因**：noRollbackFor是"一刀切"，所有BusinessException都不回滚，没法区分是"addCoins送币的业务异常（应该吞不回滚外层）"还是"打卡重复的业务异常（应该回滚外层）"。
**最终解法**：绝对不要用noRollbackFor方案解决A001。正确方案永远是内层改REQUIRES_NEW。
**下次禁止犯的错**：noRollbackFor只能用在"这个方法100%确定不需要回滚任何异常"的极端场景，QA环境禁止用noRollbackFor作为临时补丁。

### A005 · REQUIRES_NEW新事务独立连接导致读不到外层未提交修改问题
**现象**：如果addCoins方法里需要读外层主事务刚save完的wish_order实体→REQUIRES_NEW新事务/新DB Connection→读不到未提交修改→NullPointerException。
**根因**：REQUIRES_NEW物理隔离=新事务新连接。外层主事务save完EntityManager.flush了但没commit（还没走到return），独立新事务用MVCC读不到未提交版本。
**最终解法**：addCoins方法参数传全所有需要的数据（比如reason、customDelta、fromUserId），不要再去读外层刚save的实体。CoinService.addCoins目前设计就是参数全传，不需要读外层业务实体，所以没问题。
**30秒验证**：看CoinService.addCoins方法体里有没有调用`xxxRepository.findById(外层刚save的id).get()`→如果有就改成外层参数传进来。
**下次禁止犯的错**：REQUIRES_NEW内层方法不要依赖外层未提交的实体状态，所有需要的数据都参数传全。

## B. 🛠 Java编译类（枚举/lombok/方法重载）

### B001 · ErrorCode.getCodeValue() 找不到符号
**现象**：
```
java: 找不到符号
  符号:   方法 getCodeValue()
  位置: 类型为com.xindong.common.enums.ErrorCode的变量 SYSTEM_BUSY
```
**根因**：ErrorCode枚举字段名是`code`（不是`codeValue`），lombok @Getter生成的是`getCode()`不是`getCodeValue()`。误以为枚举类有自定义的getCodeValue()方法。
**最终解法**（3层保险，优先级从高到低）：
1. 方案A（最推荐，100%不调任何getXxx）：`Result.error(ErrorCode.SYSTEM_BUSY, "自定义msg");` 直接传枚举对象+自定义msg，用Result的(ErrorCode, String)重载方法
2. 方案B（兜底万能）：`Result.error(ErrorCode.SYSTEM_BUSY.getCode(), "自定义msg");` @Getter 100%生成getCode()方法存在
3. 方案C（终极兜底硬编码）：`Result.error("50002", "自定义msg");` 写死错误码
**30秒快速定位**：打开ErrorCode枚举类→看字段名→看@Getter有没有→然后选方案A。
**下次禁止犯的错**：调用枚举方法前先看一下类里的字段名，不要凭经验想当然写getCodeValue/getMsgValue。优先用Result.error(枚举, msg)重载方法，不用调getter=不会有找不到符号问题。

### B002 · lombok @Getter @Setter @Builder 编译期生成，IDEA缓存红波浪但Rebuild后过
**现象**：IDEA编辑器里User.builder()/ErrorCode.getCode() 报红波浪找不到符号，但菜单Build→Rebuild Project后javac编译成功。
**根因**：lombok是编译期（javac）注解处理器，在AST阶段生成getter/setter/builder方法字节码。IDEA的增量编辑器索引有时会漏处理lombok注解，导致编辑器静态分析误报。
**最终解法**：忽略编辑器红波浪→Build → **Rebuild Project**（不是普通Ctrl+F9）→如果还红→File→Invalidate Caches/Restart→清索引重启IDEA。
**30秒验证**：打开Build→Rebuild Build Output看有没有编译错误。没有报错=代码没问题，只是IDEA缓存。
**下次禁止犯的错**：不要为了消除IDEA红波浪手写getter/setter破坏项目lombok一致性。

### B003 · Result.error 重载方法匹配失败
**现象**：`Result.error(ErrorCode.SYSTEM_BUSY, "msg")` 报"Cannot resolve method 'error(ErrorCode, String)'"。
**根因**：项目里Result类的静态工厂方法重载不全，只有`error(String code, String msg)`，没有`error(ErrorCode, String)`重载。
**最终解法**：要么在Result类里补`error(ErrorCode codeEnum, String customMsg)`重载方法（推荐，项目统一风格），要么立刻切方案B用枚举.getCode()传String。
**30秒快速定位**：打开Result.java类→搜public static Result error→看所有重载方法签名。
**下次禁止犯的错**：调用静态工厂方法前，先快速看一下类里的重载方法有哪些，不要假设一定有(ErrorCode, String)版本。

### B004 · RequiredArgsConstructor 与 final 字段组合导致构造器漏字段
**现象**：GlobalExceptionHandler用@RequiredArgsConstructor，但注入的字段不是final→构造器没注入→运行时NPE。
```java
@RequiredArgsConstructor // 只会为final字段生成构造器参数
public class GlobalExceptionHandler {
    private JwtUtil jwtUtil; // 不是final→没注入→NPE
```
**根因**：lombok @RequiredArgsConstructor规则：只为所有**final字段**和所有**@NonNull注解字段**生成构造器参数。普通字段不会被包含。
**最终解法**：要么把注入字段加final，要么改成@AllArgsConstructor，要么改成@Autowired字段注入（不推荐）。
**30秒检查**：类上@RequiredArgsConstructor→所有依赖注入字段是不是final或@NonNull。
**下次禁止犯的错**：@RequiredArgsConstructor的类里注入字段必须加final。

## C. 📜 PowerShell脚本交付类（用户批评过多次，必须100%遵守）

### C001 · 把.ps1多行内容直接贴聊天让用户复制→100%报错（用户最痛恨，批评过3次）
**现象**：
```
表达式或语句中包含意外的标记"}"
System.ArgumentOutOfRangeException: 该值必须大于或等于零...参数名: top 实际值是 -10
=ConvertTo-Json : 无法将"=ConvertTo-Json"项识别为 cmdlet...
```
**根因**：PowerShell多行脚本复制到命令行窗口时：① 中文编码不对（非UTF8 with BOM）→乱码导致括号配对/字符串引号错乱；② 换行拆分时一行变多行拆到一半→语法分析器崩溃；③ 命令缓冲区大小溢出（System.ArgumentOutOfRangeException top=-10）→控制台输出折行时异常。
**最终解法**：① 脚本内容必须用Write工具**写入磁盘scripts/目录下的.ps1文件**，保存为**UTF-8 with BOM**编码；② 聊天里**只给用户一条单行执行命令**，形式固定为：
```
Set-ExecutionPolicy Bypass -Scope Process -Force ; powershell -NoProfile -NonInteractive -ExecutionPolicy Bypass -File "f:\docker\scripts\NNN-脚本名.ps1"
```
③ 用户复制这一整行回车就跑完，全程不用复制多行内容/打开脚本。
**30秒检查合规**：聊天输出里有没有出现```powershell```代码块包含≥3行连续命令？→有的话=违规，必须改成写磁盘+单行-File命令交付。
**用户批评次数**：3次以上（056/058/061轮规范写入第10条第11条铁律）。
**下次禁止犯的错**：哪怕用户说"给我命令让我执行"→如果命中断脚本触发条件（≥3条命令/含if变量循环/超一屏）→必须先生成脚本写磁盘+给单行命令，绝不能贴多行。

### C002 · Windows PowerShell .ps1 没保存为UTF-8 with BOM→中文全乱码
**现象**：脚本执行时所有Write-Host中文变成乱码：`涓嬩竴姝ラ獙璇侊細1. 鎵撳紑鏈€鏂?report_*.html...`
**根因**：Windows PowerShell 5.1默认读.ps1脚本是系统默认ANSI编码（GBK）。如果脚本保存成UTF-8 without BOM（大多数编辑器默认）→中文被当成GBK解码→全乱码。只有UTF-8 with BOM（文件头3字节EF BB BF）PowerShell才会识别成UTF-8。
**最终解法**：写.ps1脚本时必须强制保存为UTF-8 with BOM编码。Write工具写时先加BOM前缀字节（0xEF,0xBB,0xBF）+ 内容。
**30秒验证**：右键.ps1→打开方式→记事本→文件→另存为→看底部编码下拉，如果是"UTF-8"（不是"带有BOM的UTF-8"）→就是没BOM版，会乱码。
**下次禁止犯的错**：任何.ps1脚本交付前先确认编码是UTF-8 with BOM。不要用默认编辑器保存。

### C003 · `cd路径` 和 `命令` 中间没有分号或换行导致命令行参数粘连
**现象**：用户执行时找不到文件或报"'f:\docker\xxx.py' 不是内部或外部命令"。示例：
```
# 错误写法（粘连）：
cd f:\docker\xindongpython test_runner.py --all（xindong和python粘连成"xindongpython"）

# 正确写法（分号）：
cd f:\docker\xindong-station ; python "f:\docker\任务1\测试\_自动化测试工具\test_runner.py" --all
```
**根因**：单行多命令必须用PowerShell的分号`;`分隔符。Windows cmd用`&&`，但PowerShell里`&&`是PowerShell 7+才支持，旧版PowerShell 5.1会报错不识别`&&`。所以跨PowerShell版本安全写法永远是分号`;`。
**最终解法**：所有单行拼接命令（cd+执行+...）全部用` ; `（前后空格+分号）分隔。路径永远加双引号防止有空格。
**30秒检查**：所有单行复合命令里有没有至少2段之间是` ; `分隔？→没有就补上。
**下次禁止犯的错**：不要用&&连接cd+命令（PowerShell 5.1不支持），统一用分号`;`。

### C004 · 多行条件判断/循环/函数写在单行太长→800字符超一屏
**现象**：单行命令超过800字符/20行，用户复制时中途截断/折行出错，或者根本看不清写了啥。
**根因**：规范第9条触发条件③：命令总长度超过一屏（≈800字符）=必须生成脚本，不能只写单行拼接。
**最终解法**：直接写.ps1脚本拆成多行+逐步骤注释。
**下次禁止犯的错**：看到命令越写越长→立刻停下写脚本，不要硬往单行塞。

### C005 · 脚本头部缺少 $ErrorActionPreference = "Stop" → 错误静默继续污染
**现象**：脚本第1步MySQL连接失败→脚本还在继续跑第2步reset→第3步测试→结果完全不可信。
**根因**：PowerShell默认$ErrorActionPreference = "Continue"→命令失败（非0退出码）时默认继续往下跑。必须在脚本开头设置为Stop→遇到任何错误立刻停止。
**最终解法**：所有.ps1脚本前2行固定写：
```powershell
#Requires -Version 5.1
$ErrorActionPreference = "Stop"
```
还要每个关键命令执行后检查`if ($LASTEXITCODE -ne 0)`（Python/exe等外部程序退出码）→非0立刻写红色报错+exit非0。
**30秒检查**：任何.ps1脚本打开前3行有没有上面2行？→没有=不合格。
**下次禁止犯的错**：写脚本时先写这2行再写其他内容。错误不停止=测试结果100%不可信。

### C006 · 缺少 Set-Location "f:\docker"（绝对路径cd）→ 用户右键运行路径不对
**现象**：用户在其他目录（比如C:\Users\xxx）右键"用PowerShell运行"脚本→脚本里的相对路径`./scripts/056.ps1`/`./xindong-station`全找不到。
**根因**：PowerShell右键运行时的工作目录是用户的Documents文件夹或C:\Windows\System32，不是脚本所在目录。必须用绝对路径cd到正确工作目录兜底。
**最终解法**：脚本开头第3步内必须有`Set-Location "f:\docker"`（写死绝对路径），或用`Split-Path $MyInvocation.MyCommand.Path`自动取脚本所在目录cd过去。
**30秒检查**：打开.ps1脚本前10行有没有Set-Location（绝对路径）→没有=不合格。
**下次禁止犯的错**：永远不要假设用户会先cd到正确目录再跑脚本。

### C007 · "你点击运行会报错" → 用户明确禁止右键运行（必须给命令行文本）
**现象**：用户反复强调"我点击运行ps的环境有问题"→但是还是给右键运行方式→用户执行爆炸。
**根因**：用户Windows环境右键"使用PowerShell运行"有自定义策略/ExecutionPolicy限制/路径安全限制/缓冲区bug。所以必须100%走复制单行命令到命令行窗口执行的方式，不要右键。
**最终解法**：交付方式100%是给用户一段纯文本的单行命令（带-NoProfile -NonInteractive -ExecutionPolicy Bypass -File的完整参数），用户复制到打开的PowerShell/CMD窗口回车，永远不要提"右键运行"。
**用户批评次数**：2次以上（058轮）。
**下次禁止犯的错**：用户说"点击运行ps环境有问题"→100%只给复制的文本命令，不提右键。

## D. 🧪 测试脚本参数类（写死/脏数据/兜底不足）

### D001 · questionId写死=1 → 后端Seed不一定是1→30004题目不存在
**现象**：M11-002提交答案时写死`body={"questionId":1,"answer":"0"}`→后端真实Seed题库的第一题id不一定是1（可能是从101开始或UUID）→返回30004题目不存在。

## F. 📮 HTTP请求体/参数传递类（RequestBody vs Query）

### F001 · Controller用@RequestBody Map<String,Object>接收+AOP/CoolingCheck先读了body→Controller里拿不到→50002
**现象**：测试脚本用urllib.request的POST请求，body写`{"title":"脚本测"} json.dumps`→Controller方法是：
```java
@PostMapping("/anniversaries")
public Result save(@RequestBody Map<String, Object> body) { ... }
```
→后端返回50002，DEBUG后缀"Required request body is missing"或"JSON parse error: No content to map"→但测试日志里明明有请求体内容。
**根因**：Spring默认HttpServletRequest的body InputStream只能读一次。如果AOP切面（比如CoolingCheck冷启动校验/日志切面）在Controller之前先调用了`request.getReader()`/`getInputStream()`读了body→到Controller里的HttpMessageConverter再读时→InputStream已经到末尾=空→body没了。
**最终解法**（短期QA方案，绕过问题）：Controller新增**query兼容方法**（后缀加/q）→用@RequestParam接收参数，不依赖RequestBody：
```java
@PostMapping("/anniversaries/q")
public Result saveQ(@RequestParam String title, @RequestParam String targetDate, @RequestParam String type) { ... }
```
测试脚本切query接口：`send("POST", "/anniversaries/q", params={"title":"xx","targetDate":"xx"})`。
（长期开发方案）：自定义RequestBody Advice过滤器把InputStream缓存成可重复读的ContentCachingRequestWrapper→AOP和Controller都能读。
**30秒快速定位**：DEBUG后缀是Required request body is missing→先怀疑F001→立刻切query接口验证→能过=确认是body被AOP消耗。
**出现次数**：M03打卡、M04日记、M05纪念日共3个模块都遇到过。
**下次禁止犯的错**：QA脚本遇到RequestBody Map类的50002→第一反应切query兼容方法验证，不要在那纠结JSON格式。

### F002 · @RequestBody 实体类参数名和JSON字段不一致→@JsonProperty漏写→50002
**现象**：实体类字段是`coupleId`驼峰，前端/测试传`couple_id`下划线→Jackson反序列化时coupleId=null→NPE→50002。
**根因**：SpringBoot默认Jackson属性命名策略是驼峰（SNAKE_CASE要手动配置）。全局没配置spring.jackson.property-naming-strategy=SNAKE_CASE时，`couple_id`不会自动映射到`coupleId`。
**最终解法**：① 要么application.yml里加：
```yaml
spring:
  jackson:
    property-naming-strategy: SNAKE_CASE
```
② 要么字段上加`@JsonProperty("couple_id")`显式指定。
**下次禁止犯的错**：新建接口时先看全局Jackson配置，不确定就加@JsonProperty显式写。

### F003 · @RequestParam required=true传空字符串/没传→400 Bad Request→脚本expect_http=200→FAIL
**现象**：测试脚本调query接口，但漏传了required=true的参数（比如/diaries/q漏传content）→返回HTTP 400 Bad Request，Spring默认错误页→脚本expect_http=200→FAIL。
**根因**：@RequestParam默认required=true，没传参数时Spring直接返回400，根本进不了Controller业务逻辑→所以code=0断言永远不成立。
**最终解法**：写query兼容方法时，所有@RequestParam先加`required = false`→Controller内部自己校验"空=param error→30001"→统一返回HTTP200业务错误→和项目风格一致（所有业务错误都是HTTP200+body里code）。
**下次禁止犯的错**：所有Controller方法的入参默认`required = false`，业务校验在方法内做→统一返回HTTP 200。

### F004 · DELETE /xxx/9999 返回HTTP 404 Not Found→脚本expect_http=200→FAIL
**现象**：M05-005跨情侣删不存在的id=9999→后端抛BusinessException(ErrorCode.NOT_FOUND, ...)→GlobalExceptionHandler里返回HTTP 404→脚本断言expect_http=200→FAIL。
**根因**：规范约定所有业务错误（包括NOT_FOUND）HTTP都是200？还是业务错误码对应真实HTTP状态（404=404，403=403，409=冲突）？项目里两种都有，不统一。
**最终解法**：测试脚本断言时expect_http**不要写死200**→要么写`expect_http=None`（HTTP code不管只看body里code），要么查ErrorCode枚举里有没有写对应的httpStatus（NOT_FOUND=404，FORBIDDEN=403，CONFLICT=20701→409）→对应写正确expect_http。
**下次禁止犯的错**：所有业务错误（非0 code）的接口测试→先查ErrorCode对应HTTP状态→不要想当然写200。

### F005 · urllib.request POST Content-Type没设application/json→后端@RequestBody拿不到→415 Unsupported Media Type
**现象**：send方法POST JSON时漏设`Content-Type: application/json`头→后端HttpMessageConverter找不到匹配的→返回HTTP 415。
**根因**：urllib.request默认Content-Type是application/x-www-form-urlencoded，传JSON必须手动加header。
**最终解法**：test_runner.py的send函数里，POST方法+body是dict的→自动headers加`Content-Type: application/json; charset=utf-8`。

### F006 · 静态资源404（/quiz/today /xxx.html）被全局异常Handler转成50002→看不到是404

```java
}
```

## H. ⚙️ IDEA Build vs Rebuild差异类（最隐蔽的"重启没用"原因）

### H001 · 改了@Transactional(REQUIRES_NEW)后按普通Run→AOP代理类没重编→旧class没生效→用户说"我已经重启过了还是不行"
**现象**：按079的方案改了CoinService.addCoins上的@Transactional加REQUIRES_NEW→按Run→"Restart 'Application'"按钮→跑测试还是Transaction崩溃→用户说"我已经重启过了不是这个原因"→但实际上class文件还是旧的！
**根因**：IDEA普通Run/Restart触发的是**增量编译**（只Build修改过的单个java文件）。Spring AOP事务代理类（CoinService$$EnhancerBySpringCGLIB$$xxx.class）是编译期或类加载时动态生成的。只改@Transactional注解属性→增量编译有时不会触发AOP代理类重新生成→运行时调用的还是旧代理（默认REQUIRED传播）→REQUIRES_NEW完全没生效。
**最终解法**：只要改了任何AOP相关注解（@Transactional/@Async/@Scheduled/@Around/@Aspect）→必须走：**菜单Build → Rebuild Project**（不是Ctrl+F9 Build Project！Rebuild会清空所有class重新编译所有类+所有AOP代理类100%重生成）→然后红色Stop按钮停止进程→Run全新启动（不是Restart按钮！Restart还是用旧的缓存）。
**30秒验证真生效**：① 后端启动后看CoinService.addCoins里打一行log.info("REQUIRES_NEW生效? propagation="+TransactionAspectSupport.currentTransactionStatus().isNewTransaction())→返回true=是新事务=生效，false=没生效；② MySQL show processlist看addCoins执行时是不是有2个不同的Connection ID（外层主业务1个+addCoins独立事务1个）=REQUIRES_NEW生效。
**用户批评次数**：1次（079轮用户说"已经重启过了，不是这个原因"→浪费了整整2轮排查）
**下次禁止犯的错**：任何AOP/切面/事务/传播属性/锁级别改动→100%走Rebuild Project + Stop + Run，绝对不要偷懒按Run或Restart。

### H002 · lombok注解处理器增量编译失效→getter/setter找不到→H001连带问题
**现象**：改了lombok @Data字段→Run后报User.getPhone()找不到→但Rebuild后又过了。和H001同根因：lombok注解处理器是编译期插字节码→增量Build有时漏处理→class文件里没生成getter/setter方法。
**最终解法**：任何lombok相关（加字段/改注解/加@Builder/@Data）→同样必须Rebuild Project。
**下次禁止犯的错**：看到"找不到符号getXxx/setXxx/builder"但代码里明明有@Data/@Getter→先Rebuild再说，不要怀疑代码写错。

### H003 · Spring Boot DevTools热更新（spring-boot-devtools依赖）类加载器隔离→改动不生效
**现象**：引入spring-boot-devtools做热部署→改了Java代码Ctrl+F9后热加载生效了→但事务/缓存/Redis等共享状态不一致→行为诡异（比如送币了但流水没写，或写了流水但外层回滚）。

**下次禁止犯的错**：pom.xml看到spring-boot-devtools→测试环境注释掉。

## J. 🧪 业务逻辑"静默Bug"测试类（接口code=0但业务结果不符合预期）

> 定义：前端显示"操作成功"、后端接口返回`code=0`，但**实际业务数据不符合预期**（次数没扣、数据没存、余额不对、状态错误）。这类Bug不会直接报错/崩溃，但用户体验最差（以为操作成功了，回头发现白做了），是QA最容易漏测的。

### J001 · 通用测试方法论：业务断言 + 前后台交叉对账（★核心方法，所有模块必须执行）
**现象**：现有UI巡检脚本（e2e_ui_patrol.py）只检查"页面能不能打开、有没有报错"，完全没检查业务逻辑正确性。用户实际遇到：转盘抽了3次还是显示剩余6次、打卡"添加成功"但再进入没记录。
**根因**：之前的自动化=仅"可达性/渲染"检查，没有"操作→读接口真实值→比对"的业务断言层。UI测试≈只看页面白不白，不验证账对不对。
**最终解法**（3步标准流程，所有写操作模块都要套）：
```
步骤1【操作前快照】：进入页面 → 前端展示值记下来F1 → 调后端GET接口拿真实值B1 → 断言F1=B1（展示正确基础）
步骤2【执行用户操作】：模拟点击抽奖/提交/勾选/删除等写操作 → 等待前端Toast提示成功
步骤3【操作后对账】：前端展示值F2 → 再次调后端GET接口拿真实值B2 → 断言3件套：
  断言A：F2 == B2（前端显示和后端真实一致，没有"显示成功但没存"）
  断言B：B2 符合业务变化量（比如B2 = B1 - 1，扣减了）
  断言C：B2 没有越界（比如0 ≤ B2 ≤ MAX_DAILY_SPINS，不超上限不为负）
```
**30秒快速定位是否漏测**：打开e2e_ui_patrol.py → 搜有没有`requests.get`调API拿真实值的代码？→搜有没有`assert 前端 == 后端`的业务断言？→两个都没有=当前脚本完全没测业务正确性=必须补。
**出现时间**：2026-08-15 用户问"还有那种不符合预期结果的bug怎么测试"→全项目之前没有任何业务断言层，全部靠人工肉眼对。
**下次禁止犯的错**：任何自动化巡检脚本，如果只测页面渲染不测业务断言=只测了30%，剩下70%的静默Bug完全覆盖不到。UI巡检=页面可达性检查+业务断言对账，缺一不可。

### J002 · 破冰大转盘抽奖后次数不扣减 / 无限增加（用户反馈"每天的次数不固定吗，越来越多"）
**现象**：点击转盘抽奖 → 前端显示"抽奖成功" → 但是"今日剩余次数"从6变成6（没扣）；或完成一个任务后次数从3→5→7→9无限累加（超过MAX上限）。
**根因**：
1. 次数不扣减：前端`doSpin`只改UI变量但接口失败时没回滚 / 后端`spin()`没写`spinsLeft = spinsLeft - 1`扣减逻辑 / 扣减后没`cap()`限制上限。
2. 无限增加：完成任务后`spinsLeft += 2`无条件加，没有`Math.min(MAX_DAILY_SPINS, ...)`限制上限。
**最终解法**（前后端双保险）：
- 后端IcebreakService：`private static final int MAX_DAILY_SPINS = 6;` + `private static int cap(int n){return Math.max(0, Math.min(MAX_DAILY_SPINS, n));}` → 所有修改spinsLeft的地方（spin扣减、完成任务奖励）都包一层`cap(...)`。
- 前端Icebreak.vue：`doSpin`点击后**立即扣减1次UI显示**（乐观锁）→ 接口返回成功后以`spinRes.spinTodayLeft`为准覆盖 → 接口失败则把之前扣的1次加回来（回滚）。
**30秒快速对账脚本**：
```
操作前：GET /api/icebreak/status → 记录 spins_left=B1，前端显示=F1（断言B1==F1）
操作：  POST /api/icebreak/spin → 返回code=0
操作后：GET /api/icebreak/status → spins_left=B2=B1-1，前端F2==B2
再操作：连续POST spin 6次 → 第7次必须返回21102/21103次数不足，B2=0
任务奖励：POST完成任务 → B2不超过MAX_DAILY_SPINS(6)，绝对不能出现7/8/9
```
**出现时间**：2026-08-14 用户反馈"这里，每天的次数不固定吗，越来越多"→截图显示今日剩余8次→后端奖励逻辑没加上限。
**下次禁止犯的错**：所有"每日X次"类功能（转盘/问答/签到），3件事必须同时具备：①后端有MAX常量+cap()限幅函数 ②前端点击后立即扣减+失败回滚 ③测试脚本有连续操作超上限的断言。缺任何一个=下次还会出同样的Bug。

### J003 · 心情打卡提交显示"添加成功"但实际未保存（静默未写入DB）
**现象**：选择心情值+填文案 → 点"确认打卡" → Vant Toast弹出"心情打卡成功" → 返回首页再进入心情打卡页面 → 今天的打卡记录是空的（DB里没写进去）。甚至出现"心情值不合法"但Toast还是成功。

1. 前端`submitMood`里 try-catch 把后端BusinessException（比如20301重复/30001参数不合法）吞了，catch块里还是调`showToast("打卡成功")`→假成功。
2. 前端传`moodValue`是字符串"3.5"，后端int接收自动截断/抛异常→接口返回50002→前端catch吞→依旧成功提示。
3. POST /moods 接口返回code=0但受影响行数=0（DB触发器拦截/事务回滚），前端只看code不看data里的affectedRows。
**最终解法**（成功判定铁律）：
- 前端：**只有当`res.code === 0 && res.data && res.data.id`才弹"成功"Toast**，否则一律把后端`res.msg`原封不动弹出来。绝对不要写`finally { showToast("成功") }`或catch里也弹成功。
- 前端参数：`moodValue`传整数，提交前本地校验`1<=val<=5 && Number.isInteger(val)`，不合法直接拦不下发。
- 测试断言（J001通用流程套进来）：
```
POST /moods/reset-today（清脏数据）
GET /moods/today → data=null（B1=未打卡）
POST /moods body={moodValue:3,note:"test"} → code=0, data.id存在
GET /moods/today → data.moodValue=3, data.note="test"（B2=真存了）
再次POST同样的 → 必须返回20301"今日已打卡"，B3不变=B2（幂等）
```
**30秒快速验证**：前端点打卡后→不要信Toast→立刻调GET查询接口看返回有没有真实id/moodValue。查询为空=假成功Bug。
**下次禁止犯的错**：任何写操作（打卡/日记/纪念日/心愿创建）的成功提示，100%必须依赖`code===0 && data返回了主键id`两个条件同时成立，缺一不可弹"成功"。

### J004 · 金币中心数字后带"□"乱码 + 显示值与接口真实余额不一致
**现象**：金币总览"我的金币"显示为"168□"（末尾方块），或显示"0"但接口返回`coins_total=256`（数据对不上），或"获取"Tab点卡片跳转不到对应页面。
**根因**：
1. □乱码：后端返回的JSON里数字字段后面带了不可见控制字符（`\u0000`/`\u200B`零宽空格），或emoji用`🪙`(U+1FA99新版Unicode)旧版Windows/浏览器显示不出变方块。
2. 数据不显示：前端`overview.coins_total`写成`overview.coinTotal`/`overview.total`字段名和后端不匹配，undefined显示成空白。
3. 卡片不跳转：`<van-cell>`没绑`@click`或`to`属性，或路由路径写错。
**最终解法**（数据清洗+字段双兼容）：
- 前端写`safeNum(v)`清洗函数：`v==null?0:parseInt(String(v).replace(/[^\d-]/g,'')) || 0`→把所有非数字字符（控制字符/零宽空格/emoji）全删掉，强转整数。永远不要直接`{{ coins }}`显示，必须套`safeNum`。
- 前端字段双兼容：`const total = safeNum(data.coins_total ?? data.coinTotal ?? data.total)`，后端返回3种可能的字段名都能接住。
- Emoji替换：全局把`🪙`→`💰`，`🧳`→`✈️`，`🥹`→`😊`，只用2020年之前的通用emoji（U+1Fxxx早期版本），不要用U+1FAxx（2022+新版）。
- 测试断言：
```
GET /coins/overview → data.coins_total = B1（后端真实值）
前端页面读取"我的金币"数字显示 = F1
断言 F1 == safeNum(B1)，且F1不含任何□/�/控制字符
GET /coins/logs → 流水列表总条数 = N1，前端显示条目数 = N2
断言 N1 == N2，每条reason/amount字段都和接口一致
```
**30秒快速验证**：前端显示的数字复制粘贴到记事本→看有没有看不见的方块/乱码字符→有就是safeNum没套。
**下次禁止犯的错**：所有后端返回的数字字段（余额、次数、ID、分页total），前端必须走`safeNum`清洗后再显示/计算，不要相信后端返回的一定是干净数字。

### J005 · 心愿详情步骤勾选前端显示打勾但后端`completedSteps`未更新（静默勾选失败）
**现象**：心愿详情5步流程→点击第2步文字"✓完成第2步"→前端立刻变成绿色打勾（用户以为成功了）→刷新页面重新进入→第2步又变回未勾选状态（DB没存）。
**根因**：
1. 点击事件只绑了`<van-checkbox>`的小方块区域，点击文字/整行没触发→用户点了文字其实没点到checkbox。
2. 前端点击后`step.completed = true`本地改了状态，但没发`POST /wishes/{id}/steps`接口→刷新就没了。
3. 接口发了但返回code=30004（心愿不存在/不是自己的）→前端catch吞了，本地状态还是true→假成功。
**最终解法**（点击热区+乐观更新+失败回滚三件套）：
- 点击热区：整行`<div class="step-row" @click="toggleStep(idx)">`包checkbox+图标+文字，整行任意位置点都触发toggle。
- 乐观更新+回滚：`toggleStep`里先记旧值`old = step.completed`→立刻本地改反`step.completed = !old`→发API→成功保留→失败`step.completed = old`（回滚）+弹错误msg。
- 测试断言（J001通用流程）：
```
GET /wishes/{id} → data.completed_steps = [1]（B1=只有第1步完成）
前端点击步骤2 → 本地显示步骤2打勾(F2)
POST /wishes/{id}/steps → body={step:2,checked:true} → code=0
GET /wishes/{id} → data.completed_steps = [1,2]（B2=后端真存了）
断言 F2显示步骤2已完成 == B2包含2
刷新页面重新进入 → 步骤2依然打勾（持久化验证）
```
**30秒快速验证**：勾选完→直接F5刷新页面→如果勾选状态丢失=假勾选Bug，别管前端当时显示多好看。
**下次禁止犯的错**：所有勾选/开关/排序等即时操作，必须遵守"本地乐观改→发API→失败回滚"三板斧。绝对不要只改本地状态不发API，也不要发了API失败不回滚。

### J006 · 破冰最近完成记录显示"破冰任务"默认名+状态"进行中"但实际已完成（字段映射错误）
**现象**：破冰大转盘下方"最近完成"列表→每条显示"破冰任务 | 进行中 | 2分钟前"→但实际用户已经点了"完成任务"提交了反思。应该是"一起做饭🍳 | 已完成 | 2分钟前"。
**根因**：
1. 标题错误：前端`normalizeHistory`里取标题时写的是`item.name ?? item.taskName ?? "破冰任务"`→但后端history接口返回的是`taskTitle`字段（新字段）→3个都没命中→落兜底"破冰任务"。
2. 状态错误：前端判断已完成的条件是`item.status === "FINISHED"`→但后端返回`status: "DONE"`→字符串不匹配→全部显示"进行中"。
3. Emoji错误：后端返回`taskEmoji=🪙`→旧浏览器显示□→前面板还是□（参见J004）。
**最终解法**（字段双兼容+枚举值白名单）：
- 字段双兼容：前端所有从后端取数据的地方写`||`链路兜底至少4层，比如标题：`item.taskTitle || item.title || item.taskName || item.name || "未命名任务"`。不要只写1种字段名。
- 状态兼容：前端写白名单判断已完成：`["DONE","FINISHED","COMPLETED","已完成"].includes(item.status) || item.finishedById || item.reflection || item.doneAt`→只要命中任何一个就当已完成，不要只比一个精确字符串。
- 测试断言：
```
POST完成任务 → code=0, 返回recordId
GET /icebreak/history → list[0] = 第一条记录
断言 list[0].taskTitle != "破冰任务"（是真实任务名，比如"一起做饭"）
断言 list[0].status ∈ {"DONE","FINISHED"} 或 有finishedById/reflection/doneAt任意字段
断言 list[0].taskEmoji 存在（不是空/undefined）
前端显示最近完成列表的第1条：标题=taskTitle，状态=已完成，emoji显示正常无□
```
**30秒快速验证**：history接口返回的JSON→直接找前端代码里对应显示用的字段名→如果前端要的字段不在JSON里→必出默认值Bug。
**下次禁止犯的错**：前端对接后端接口时，字段不要用精确匹配硬写1个，永远用4层以上兜底兼容；枚举状态不要只匹配1个字符串，永远用白名单数组+多字段判断。

### J007 · 金币overview接口不返回coupleId导致脚本调用internal-add时传coupleId=0→30001参数错误
**现象**：biz_assert_only.py静默对账脚本J008用例（金币负数钳位兜底）执行流程：
```
1. GET /coins/overview → code=0，拿到data={coins_total:100, coins_available:90, ...}（但没coupleId字段）
2. 脚本从overview响应里取coupleId → 取不到=默认0
3. POST /coins/internal-add body={"couple_id":0,"delta":-101,"allow_negative":false}
4. 后端返回code=30001 msg="参数错误：coupleId不能为空或0"
```
接口code≠0，但脚本以为是接口本身问题，实际是脚本传参错，属于"对账前准备步骤传参静默错误"，会导致后面的负数钳位断言永远跑不到。
**根因**：
1. 后端CoinService.getOverview方法返回的Map里漏了`coupleId`字段——CoinOverview的DTO定义有coupleId字段，但Service实际组装返回Map时只put了coins_total/coins_available/today_earned等字段，忘了put("coupleId", coupleId)。
2. 脚本fetch_coupleid()函数设计缺陷：优先从/coins/overview取coupleId，但overview不返回时没有fallback（比如调/couple/info接口拿），直接静默默认0，导致传参错误但日志里看不出是"没拿到coupleId"还是"真的传了0"。
**最终解法**（后端+脚本双保险，防止单边改完另一边又复发）：
- **后端修复（必做）**：CoinService.getOverview返回Map里强制加上coupleId字段：
```java
// CoinService.java getOverview方法末尾，return前加：
result.put("coupleId", coupleId);  // 必须和其他字段一起put，不能漏
```
同时保证不管前端/脚本需不需要，overview永远返回完整的coupleId，避免调用方各自猜。
- **脚本修复（必做）**：fetch_coupleid()函数改为3级fallback，不能只靠overview：
```python
def fetch_coupleid(token_alias: str) -> int:
    # 优先级1：/couple/info（最权威，情侣绑定信息接口一定返回id）
    ok, _, d = send("GET", "/couple/info", token_alias, quiet=True)
    if ok and isinstance(d, dict):
        cid = d.get("id") or d.get("coupleId") or d.get("couple_id")
        if cid and int(cid) > 0:
            return int(cid)
    # 优先级2：/coins/overview（如果后端修好了也能拿）
    _, _, overview = send("GET", "/coins/overview", token_alias, quiet=True)
    if isinstance(overview, dict):
        cid2 = overview.get("coupleId") or overview.get("couple_id")
        if cid2 and int(cid2) > 0:
            return int(cid2)
    # 优先级3：硬编码兜底映射（最后一道防线，脚本启动时打印warning）
    hardcode = {"A": 108, "B": 108, "POOR_A": 909, "POOR_B": 909, "C1": 109, "C2": 109}
    ret = hardcode.get(token_alias, 0)
    if ret == 0:
        print(f"[WARNING] fetch_coupleid({token_alias}) 三级兜底全失败=0，后续internal-add必30001！")
    return ret
```
- **测试断言**：GET /coins/overview → 断言data.coupleId存在且>0（不能是0/null/undefined），这是J类用例执行的前置门禁。
**30秒快速验证**：直接在浏览器或Postman调GET /coins/overview → 看返回JSON里有没有coupleId字段且值≠0。没有=J007必中招。脚本启动时加一行日志：`cid = fetch_coupleid("POOR_A"); print(f"DEBUG: coupleId={cid}")`，如果cid=0立刻停。
**下次禁止犯的错**：① 任何返回"当前情侣上下文信息"的接口（overview/dashboard/couple/info等），必须永远把coupleId作为基础字段带上，不能凭感觉"前端不需要就不返回"——脚本/联调随时要用。② 测试脚本取coupleId这类核心主键，永远要有≥2级fallback，不能只靠1个接口的1个字段名，没取到时必须打印WARNING日志，绝对不能静默默认0。

### J008 · Checklist恋爱清单勾选toggle接口前端用POST但后端是@PutMapping→40001请求方法不支持
**现象**：biz_assert_only.py静默对账脚本J010用例（恋爱清单勾选后前后台一致）执行流程：
```
1. POST /checklists → code=0, id=123 创建待办
2. POST /checklist/123/toggle → 返回code=40001 msg="请求方法不支持，请使用正确的HTTP方法"
3. 脚本以为"勾选成功"继续往下走→GET /checklists 看id=123的done还是false→断言FAIL：勾选静默失败
```
接口code不是0但不是业务错误，是HTTP方法匹配错误（405 Method Not Allowed被GlobalExceptionHandler转成了40001业务码），属于"前端/脚本和后端Controller注解HTTP方法不一致"导致的静默勾选失败。
**根因**：
1. 后端ChecklistController.toggleDone方法注解是`@PutMapping("/checklist/{id}/toggle")`——设计上用PUT语义（更新资源状态）没问题，但前端/脚本默认习惯用POST打所有写接口，没看Controller注解。
2. 后端同时支持两个路径前缀`/checklist`和`/checklists`（兼容旧前端），但toggle接口只在`/checklist/{id}/toggle`上写了@PutMapping，没有在`/checklists/{id}/toggle`上也加一份映射，路径不对也会报方法不支持。
3. 脚本j010_checklist_toggle函数写死了method="POST"，没有try-put-first的fallback机制，遇到PUT接口直接炸。
**最终解法**（后端+脚本+前端三方对齐，避免互相甩锅）：
- **后端修复（必做）**：① toggle接口同时支持POST和PUT两种HTTP方法（双写兼容，不用改前端）；② 同时支持/checklist和/checklists双路径前缀：
```java
// ChecklistController.java 原@PutMapping改成：
@RequestMapping(value = {"/checklist/{id}/toggle", "/checklists/{id}/toggle"}, 
                method = {RequestMethod.PUT, RequestMethod.POST})
public Result toggleDone(@PathVariable Long id, Authentication auth) { ... }
```
用@RequestMapping同时指定value数组+method数组=4种组合全兼容（PUT /checklist/xxx、POST /checklist/xxx、PUT /checklists/xxx、POST /checklists/xxx都能进）。
- **脚本修复（必做）**：j010_checklist_toggle函数改为"PUT优先，失败自动fallback POST"的双尝试机制：
```python
def j010_checklist_toggle(item_id: int, token_alias: str):
    # 第1次尝试：PUT（后端原生推荐语义）
    ok1, code1, d1 = send("PUT", f"/checklist/{item_id}/toggle", token_alias, quiet=True)
    if ok1 and str(code1) == "00000":
        return True, d1
    # 第2次尝试：POST（旧前端/脚本习惯）
    ok2, code2, d2 = send("POST", f"/checklist/{item_id}/toggle", token_alias, quiet=True)
    if ok2 and str(code2) == "00000":
        return True, d2
    # 都失败=打印真实错误（不要静默吞）
    print(f"[J010-ERROR] toggle {item_id} PUT code={code1}, POST code={code2}")
    return False, None
```
- **测试断言**：勾选后必须做"前后台对账"：toggle返回code=0 → 立刻GET /checklists → 找到同id的item → 断言`done == true`（或`completed==true`/`status=="DONE"`），不能只信toggle接口的code=0。
**30秒快速验证**：打开ChecklistController.java → 搜toggle方法 → 看@RequestMapping的method数组里有没有PUT和POST两个，value数组里有没有/checklist和/checklists两个。缺任何一个=J008必中。脚本遇到40001时先Grep Controller里的HTTP方法注解，和脚本send的method对比=1分钟定位。
**下次禁止犯的错**：① 后端写任何写操作接口（更新状态/切换开关/toggle类），如果不是特别强调REST语义（比如纯PATCH才支持），默认就@RequestMapping同时写PUT+POST双方法兼容，不要搞"我用PUT才是正确的前端必须改"这种纯理论洁癖。② 脚本写任何toggle/切换类接口调用，必须双方法fallback（PUT先POST后或反过来），不要写死1种。③ 写操作后必须立刻读一次做对账，不能信接口返回code=0就完事（J类静默Bug核心方法论）。
